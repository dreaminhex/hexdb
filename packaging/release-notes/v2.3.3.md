HexDB 2.3.3 makes lattices easier to grow and to watch, adds one connection URI for every driver, and introduces HexDB for VS Code.

## Added

- **Connection URIs.** Every driver takes the same connection string: `hexdb://[login[:password]@]host[:port][/path][?apiKey=...&timeout=...&pageSize=...&caFile=...]`, or `hexdbs://` for HTTPS. `hexdb://` defaults to port 7700, `hexdbs://` to 443, and a path is kept for a HexDB behind a reverse proxy. JavaScript (`new HexDB(uri)`, `HexDB.connect(uri)`), Python (`HexDB(uri)`), .NET (`new HexDBClient(uri)`, `HexDBClient.ConnectAsync(uri)`), Entity Framework (`UseHexDB(uri)`), JDBC (`jdbc:hexdbs://...`) and ODBC (`Server=hexdbs://...`). Plain `http://` and `https://` URLs still work. See "Connection URIs" in the MANUAL.
- **Replica lag in time.** `/status` reports each streaming replica's `lag_ms` next to `lag`: the age of the oldest change it hasn't applied yet, 0 when it's caught up (`network.lattice.hexes[].lag_ms`, and `replication.lag_ms` on a replica). The Overseer measures it exactly; other hexes show what each replica reported in the last discovery round. The dashboard's lattice card shows "7 ms behind (12 changes)" or "in sync · 0 ms".
- **Readiness.** `GET /ready` answers 503 until a hex can serve its data: while a replica's first full sync is running, or while a new Overseer collects slices. `/health` still answers as soon as the API listens. Use `/ready` for load balancer and Fly.io checks and Kubernetes readiness probes (the Helm chart does).
- **HexDB for VS Code**, a new extension (published separately): browse a lattice's hexes, regions and lag, tessellations and functions; run SQL and GraphQL with tabbed results; edit documents and stored functions.

## Changed

- **Discovery learns hexes from each other.** A hex that probes another is probed back, and every hex shares the hexes it sees, so one seed address in `network.peers` is enough for a new hex to find the whole lattice and for every member to find it. Learned addresses are forgotten after 30 rounds without mention, at most 64 are kept, and only hexes holding the lattice key are learned.
- **JDBC:** a bare `jdbc:hexdb://host` without a port now means port 7700 (HexDB's default), not 80. Give the port, or use `jdbc:hexdbs://` for HTTPS on 443.
- **.NET:** a base path in the URL (`https://example.com/hexdb`) is kept for every request; before, it was dropped.
- The release container image is built from the release's binaries, so it's published within minutes of the release instead of hours.

## Fixed

- **Replicas behind a new Overseer resume** from the latest position they share with it, instead of copying everything again.
- A hex that started on demand behind a load balancer no longer got traffic before its first sync finished (sessions answered 401 and fresh writes weren't readable until it caught up); see `/ready` above.
