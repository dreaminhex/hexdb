HexDB 2.7.0 (in progress).

## Point-in-time restore

- **Back to any moment of the last week.** With `backup.continuous.*` set in the lattice configuration, the Overseer ships base backups, file content and every WAL segment to an S3-compatible store (AWS S3, Cloudflare R2, Backblaze B2, Google Cloud Storage, MinIO, RustFS, Tigris), at most `max_lag_seconds` (60) behind the lattice, all of it encrypted with the storage key. `hexdb restore --until <time>` rebuilds a data folder as the lattice was at that moment, documents and file content included, never splitting a transaction. Retention is 7 days by default. `GET /backups/continuous` and a dashboard card show what's shipped and the oldest moment a restore can reach; shipping that fails for 10 minutes alerts administrators on every alert channel. WAL segments aren't pruned before they're shipped.

## Customer-managed keys

- **The storage key, wrapped by AWS KMS or Azure Key Vault.** With `[storage.key]` the configuration holds only the storage key wrapped by a key in the lattice owner's key service; each hex unwraps it at start and keeps it in memory only. Every `check_minutes` (15) it asks again: if the key was disabled or deleted, or the credentials lost permission, the hex audits `storage.key_revoked`, alerts administrators on every channel, writes out what it holds and stops, and won't start until the key is usable. A key service outage is only a warning. `hexdb keys new|wrap|rewrap|check` make, convert, rewrap (no data rewritten) and check keys. Nothing on disk changes format; "Add a hex" and `hexdb lattice spawn` hand out the wrapped key, never the unwrapped one. Requests are signed in HexDB (SigV4, checked against AWS's published test suite), with no new dependencies.

## Partitioned writes (preview)

- **Several groups of hexes, each with its own Overseer and its own share of the 64 slices.** Behind `partitioning.enabled`, off by default and not for production data yet.
  - `PUT /status/partitions` splits a lattice while it's still empty.
  - Each partition's hexes elect their own Overseer, with their own quorum, acknowledgements, handovers and replication.
  - Inserts commit on the hex that gets them: a new document's ID falls in that hex's partition. Changes to existing documents go to the partition that owns them. Users, keys, the configuration and tessellation definitions go to partition 0, which every other hex follows through a system stream.
  - Reads: a document read goes to its partition; queries, listings, counts and `GET /changes` (with a per-partition cursor) are merged from every partition.
  - Each partition is backed up on its own (`scope=hex`), and point-in-time restore ships each under `<prefix>/partition-N`.
  - Refused until a later stage, with nothing written or no partial answer: transactions across partitions, upserts, cascading deletes, aggregations, SQL, GraphQL, similarity search and live change streams.
  - Details in the manual and `design/partitioning-stage-2.md`.

## Queues

- **About nine times faster.** A send, receive, acknowledgement, release or extension now stores all its messages in one commit, instead of one commit (and one write to disk) per message. On the benchmark laptop a receive of up to 10 messages took 11 ms instead of 98 ms (median), and consumers took about 1,880 messages a second instead of 204, with or without a dashboard polling the counts (`hexdb_bench -- compare --only queues`). Each call is also all or nothing now: it stores every message it names or none. A dedupe key repeated within one send is skipped like one sent earlier, and a receipt given twice in one call counts once.

## Dependencies

- **jiff 1.0.** HexDB's date and time code (and the patched EXIF reader in `vendor/nom-exif`) moved from jiff 0.2 to its first stable release. Formats on disk, between hexes and in the API are unchanged; the clock's format tests and the SQL, schedule and metadata date tests pass as before.
