HexDB 2.0 adds AI access to your data (an MCP server and a built-in chat), sharing links, queues, gRPC and WebSocket, and runs file parsing in a sandbox. It's also the most thoroughly security-reviewed release so far. Every feature is described in the [manual](https://github.com/dreaminhex/hexdb/blob/main/MANUAL.md).

## New

**AI and agents**
- **MCP server** at `POST /mcp` on every hex, for Claude Desktop, Claude Code and other MCP clients. Its tools only read: list and describe tessellations, query, search, get, count, aggregate and SQL `SELECT`. Every call runs as the API key's user, with their permissions, row filters and hidden fields. It calls no AI provider: the client brings its own model.
- **AI chat** (the admin UI's Ask page and `POST /ai/chat`): answers questions about the lattice's data with your configured provider, using the same read-only tools as the asking user. Spending is capped: a cheaper chat model, tokens per answer and per question, per user and per client address per day, questions per minute, and the lattice's monthly budget. Off by default (`ai.chat.enabled`).

**Files**
- **Sharing links**: give people without an account a file or a folder through an 8-character link (MAR-62 codes), with expiry, an optional password and a download limit.
- **Upload quotas** per user, in bytes and files, with defaults for everyone.
- **Import plugins** for S3 and S3-compatible stores, Azure Blob Storage, Google Drive and Dropbox. They keep folders, and changed files come in as new versions.
- **More metadata**: PDF body text (searchable), embedded ICC color profiles (`color_profile`), and GoPro telemetry: the camera, its sensors and a GPS summary and track. Existing files are read again once, in the background; AI tags are kept.
- **Faster startup** for large file stores: sealed pack files keep an index of their records.

**Interfaces**
- **gRPC** (`hexdb.v1.HexDB`) on the API port. Each call runs as the matching REST request, so permissions, row filters and quotas are identical. The proto is in `hexdb_api/proto`.
- **WebSocket** feeds: `GET /changes/ws` and `GET /streams/{name}/ws` carry the same events as the Server-Sent Events feeds.
- **Queues**: messages for competing consumers, with leases, acknowledgements, retries, delays, de-duplication and dead-letter queues (`/queues`, and a Queues page in the admin UI).

**Running HexDB**
- **Parser sandbox**: metadata extraction, thumbnails and video frames run in a separate worker process without access to the store, the keys or the network. On Linux it's limited further by resource limits and a seccomp filter; on Windows it runs in a job object.
- **Crash recovery and restarts**: an unclean shutdown is reported on the next start (in `/status`, the audit trail and the dashboard). `hexdb start -s` now restarts a crashed server, and background tasks that panic are restarted too.
- **Windows service**: `hexdb service install` runs HexDB at startup under its own restricted account, with automatic restart after a crash.
- **ARM**: CI runs the whole test suite on 64-bit ARM (the Raspberry Pi 4 and 5 architecture), and 32-bit ARM builds from source. The manual has a section on running HexDB on a Pi.

## Security

Three security reviews went into this release. Fixed along the way:
- Replicas now verify signed answers from the Overseer, so documents can't be injected in transit on a link between hexes without TLS.
- Sign-in, sharing-link and chat limits count IPv6 clients by /64, so rotating addresses doesn't reset them.
- A sharing link's download limit counts bytes, so range requests can't get around it.
- The Debian and Homebrew installers create the storage key file private from the start (it was briefly readable by other local users).
- The CLI won't send a token over plain HTTP to another machine, and the Python driver no longer sends the API key along a redirect to another server.
- A queue can only send failed messages to a dead-letter queue its maker can write to.
- Results from the parser worker are checked again by the server, so a hostile file that took over the worker can't store oversized metadata or a fake thumbnail.
- Password checks on a signed-in account (changing the password, MFA) count toward the sign-in lockout.
- Only the `/lattice/*` routes hexes use are public, and function code is visible to administrators only.
- The Docker Compose file runs HexDB with a read-only file system, no Linux capabilities and no privilege escalation.

## Upgrading

- **Lattices**: upgrade the replicas first, then the Overseer. A 2.0 replica accepts unsigned answers from a 1.6 Overseer during the upgrade.
- **Re-extraction**: the first time a 2.0 hex becomes the Overseer, it reads files extracted by 1.6 again in the background, which takes a while on large stores.
- **New tessellations** can't be named `queues`, `shares` or `mcp`. Existing ones of those names keep working.
- **`hexdb start -s`** now runs the server under a small supervisor that restarts it after a crash. Add `--no-restart` for the old behavior.
- **CLI**: sending `--token` over plain HTTP to another host now fails; use HTTPS, or set `HEXDB_ALLOW_PLAINTEXT=1` on a network you trust.
- **Demo mode** (`security.demo_mode`): only administrators can change an account's password or MFA.
