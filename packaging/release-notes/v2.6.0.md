HexDB 2.6.0 lays the groundwork for partitioned writes: a partition map with epochs that forwarded requests carry. Every lattice is still one partition, so nothing behaves differently. It also moves HexDB's own date and time code off the unmaintained chrono crate, adds a benchmark mode for comparing two versions, and builds the Intel macOS release much faster.

## Partitioning (preview)

- **The partition map.** Partitioned writes will split the 64 slices among groups of hexes, each with its own Overseer (see `design/partitioning.md`). 2.6 adds the map: which partition owns each slice and which hexes form each group, with an epoch that grows with every change. A lattice that never changed it has the implicit map (partition 0, every slice, epoch 1), so upgrading writes nothing. `GET /status/partitions` (administrators) shows the map a hex routes by.
- **Epochs on forwarded requests.** With `[partitioning] enabled = true` (off by default), a hex that forwards a request also sends the epoch it routed by, covered by the lattice signature, once every live hex runs 2.6 or later. A hex with another epoch refuses the request before running it (421 `partition_epoch`), and the forwarding hex reloads its map and sends it again.

## Backups

- **A backup outlives its request.** `POST /backup` used to stop holding off flushes and compaction if the request timed out while the copy carried on, so the copy could pick up files changing under it. The backup now runs as a task of its own: it finishes with flushes and compaction held off, a second backup waits for it, and both a finished and a failed backup are audited (`maintenance.backup`, outcome `failed` with the error).
- **Backups say what they cover.** The answer to `POST /backup` and the backup's manifest now include `role`, `slices` and `complete`. A backup taken on a sliced or lagging replica (one reached through a load balancer, say) holds only part of the lattice and says so (`complete: false`); the CLI and the admin UI point to the Overseer then.

## Dependencies

- **chrono to jiff.** HexDB's own code no longer uses chrono, which is unmaintained (RUSTSEC-2026-0543). Timestamps keep exactly the same formats on disk, between hexes and in the API, and SQL date functions and schedules give the same results. The new code was checked against chrono on several hundred thousand generated dates and schedules. chrono is still compiled in through the EXIF reader. Only edge cases differ: dates past the year 9999 are refused, and a leap second (`:60`) counts as the next second.

## Files

- **Downloads through a sliced replica stream.** A file fetched by path from a replica that keeps only some slices used to be read whole from the Overseer before the first byte went out. It now streams through, ranges included, with its length.

## Benchmarks

- **Comparing versions.** `cargo run --release -p hexdb_bench -- compare <A hexdb_api> <B hexdb_api> [rounds]` runs both versions on one machine in alternating rounds. It reports p50/p95/p99 latencies, throughput with its range across rounds, and the server's memory. Both modes now stop at an answer with an unexpected status, instead of timing an error as work.

## Kubernetes

- **The first administrator's password stays out of the logs.** The Helm chart generates it into its Secret (`admin-password`, kept on upgrades) unless `admin.password` is set, so HexDB no longer generates one and prints it to the pod's log. Read it with `kubectl get secret <release>-hexdb -o jsonpath='{.data.admin-password}' | base64 -d`. With `existingSecret`, the password is now read from that Secret's `admin-password` key; earlier charts ignored it unless `admin.password` was also set. A lattice installed with an earlier chart keeps the administrator it has.

## Releases and images

- **Intel macOS** binaries are cross-compiled on Apple Silicon. The Intel build had taken 40 of a release's 50 minutes.
- **Image findings** from the 2.5.9 scan are triaged in `packaging/trivy-triage.md`: libacl1, plus TLS libraries, glibc's iconv and OpenJPEG at unknown severity. None is reachable from HexDB, and Debian has no fixes yet.

## Upgrading

Restart the hexes one at a time, as usual: replicas first, the Overseer last. Leave `partitioning.enabled` off until every hex runs 2.6.
